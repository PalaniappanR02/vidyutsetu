Check smart-meter data before it reaches your MDMS

VidyutSetu takes a meter data payload from one system format, converts it through a shared canonical model, and reports what would break on the way in: unparseable structure, unmapped fields, unit and timezone mistakes, impossible electrical values, and readings an ML screen thinks deserve a second look.

It runs in software against JSON and CSV payloads. It does not talk to meters, and it does not certify anyone’s conformance.

Who it is for

Utility AMI and MDMS engineers

Checking that a Head End System export will survive ingestion: units, timestamps, register mapping and basic physical plausibility, before a batch reaches production.

HES/MDMS integrators and QA

Reproducing a vendor’s payload, converting it to another vendor format, comparing two runs after a fix, and exporting the result as a report you can attach to a ticket.

The workflow, in four steps

  1. Choose the source and target systems

    Four formats are registered in code: Alpha (DLMS/COSEM OBIS registers), Beta (flat CSV), Gamma (CIM IEC 61968-9 JSON) and Delta (legacy milli-unit JSON). Target is optional for validation only.

  2. Provide, generate or paste a payload

    Use a sample button, generate synthetic telemetry with a meter/interval count, paste raw JSON or CSV, or upload a file.

  3. Validate it through five stages

    Parse → syntactic → semantic mapping → physical sanity → ML screening. Each stage reports pass, warning, failure or skipped, with its own duration and diagnostics.

  4. Inspect the result and export it

    The run shows an overall verdict, the most important finding, rule-by-rule diagnostics, pipeline stages and the ML opinion separately, plus an HTML report per run.

What is real, and what is not

Real, computed from your payload

Rule diagnostics
Parse, schema, mapping, unit, timestamp, monotonicity and electrical-range checks run in the code and are authoritative for the score.
Interoperability score
Weighted from those checks: syntactic 30%, semantic 40%, data integrity 30%. The result page explains each pillar.
Cross-vendor conversion and round trip
Both directions are implemented by the same adapters that validate the payload.

Advisory, synthetic, or out of scope

Advisory ML fault screening
A fault classifier and anomaly detector trained on synthetic data. They flag readings for review; they never override the rule result.
Fault types it can name
Missing field, wrong datatype, out-of-range value, duplicate reading, timestamp drift/gap, negative or rollback energy, unit mismatch, or valid.
Not implemented
No physical-layer protocol emulation (RF mesh, G3-PLC, HDLC), no certification body sign-off, no authentication or multi-tenant accounts, and no saved editing of vendor mappings from the UI — the mapping page is read-only reference.
